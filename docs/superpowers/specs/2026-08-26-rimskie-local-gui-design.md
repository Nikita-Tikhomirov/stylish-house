# Локальный графический интерфейс сборщика римских штор

Дата: 2026-08-26

## Цель

Добавить к существующему локальному сборщику понятную графическую панель управления для Windows. Пользователь не должен запускать команды в терминале или вручную искать JSON-файлы. Панель запускает полный сбор всех товаров со всех страниц 46 утверждённых категорий, показывает прогресс и позволяет безопасно продолжить работу после закрытия панели, сбоя браузера, перезагрузки компьютера или защитной паузы.

Сбор остаётся локальным. Runtime, фотографии, checkpoints и итоговый пакет хранятся только в `G:\stylish-house-data\rimskie-imports`. Сборщик не подключается к production-БД и ничего не публикует на сайте.

## Принятый вариант

Панель реализуется как локальное веб-приложение, которое запускается одной Windows-командой и автоматически открывается в обычном браузере по адресу `http://127.0.0.1:43127`. Это не страница на VPS и не публичная часть сайта.

Выбран этот вариант вместо Electron и встраивания в Laravel:

- не требуется тяжёлая desktop-оболочка и второй Chromium;
- панель может управлять уже существующим Node.js-сборщиком напрямую;
- видимый Chrome донора остаётся отдельным окном;
- приложение не получает доступ к production-БД;
- весь прогресс остаётся переносимым и восстанавливаемым из файлов на G:.

Сервер слушает только loopback-интерфейс `127.0.0.1`. Доступ из локальной сети и интернета запрещён.

## Пользовательский сценарий

### Первый запуск

1. Пользователь запускает `start-rimskie-gui.cmd` из проекта или его Windows-ярлык с русским названием `Сборщик римских штор`.
2. Локальная панель автоматически открывается в браузере.
3. Панель показывает корень данных `G:\stylish-house-data\rimskie-imports` и найденный Chrome.
4. Пользователь нажимает `Начать новый сбор`.
5. Панель создаёт новый безопасный run ID, запускает видимый Chrome и вызывает обычный режим `start` без `--max-products` и `--max-requests`. Поэтому она обходит все страницы всех 46 категорий и сохраняет все найденные уникальные товары, а не один тестовый товар на категорию.

### Текущий сбор

Панель показывает:

- статус: подготовка, работает, пауза, защитная остановка, ошибка, завершён;
- общий прогресс по 46 категориям;
- текущую категорию, номер страницы и текущий товар;
- количество обработанных страниц;
- количество уникальных товаров;
- количество сохранённых фотографий;
- количество связей товар–категория;
- общее число учтённых запросов за run и число запросов за последний час;
- обратный отсчёт до следующего запроса;
- последний URL без автоматического перехода по нему;
- последнюю ошибку или причину паузы нормальным русским текстом;
- последние события процесса.

Основные действия:

- `Пауза` — завершить текущую безопасную операцию и поставить run на паузу;
- `Продолжить` — продолжить выбранный run с checkpoint;
- `Остановить навсегда` — терминально завершить run после отдельного подтверждения;
- `Открыть папку` — открыть каталог run в Проводнике;
- `Сформировать пакет` — создать проверенный `export.json` только для завершённого run.

### Возобновление после сбоя

При новом запуске панели она сканирует только безопасные дочерние каталоги заданного data root и показывает историю run. Для каждого run отображаются дата, статус и прогресс. Кнопка `Продолжить` запускает существующую команду resume.

Checkpoint уже сохраняется после разобранной страницы категории, сохранённого товарного черновика, проверенного WebP и обновления очереди. Поэтому:

- сохранённый товар повторно не запрашивается;
- валидная сохранённая фотография повторно не скачивается;
- один товар хранится один раз, но остаётся связан со всеми найденными категориями;
- незавершённая операция может быть повторена только если процесс завершился до её durable checkpoint;
- прежняя reservation запроса остаётся в часовом бюджете.

Завершённый run не запускается повторно: для него доступны просмотр и формирование пакета. Терминально остановленный run не возобновляется.

## Архитектура

### 1. Локальный GUI-сервер

Новый Node.js-модуль запускает HTTP-сервер на `127.0.0.1:43127` и обслуживает статические HTML/CSS/JS панели и JSON API. Если порт занят другим процессом, сервер завершается с понятной ошибкой и не выбирает незаметно другой адрес. После успешного запуска точный URL автоматически открывается через Windows.

Сервер получает data root только из проверенной конфигурации. Для этой рабочей станции фиксированное значение по умолчанию — `G:\stylish-house-data\rimskie-imports`; интерфейс не предлагает выбрать произвольный путь. Техническое переопределение допускается только через существующую конфигурацию и только на другой абсолютный путь вне диска C:. Действующая защита от диска C:, junction, symlink, reparse point и hard-link сохраняется.

### 2. Supervisor процесса

GUI не дублирует логику сборщика. Он запускает существующий `cli.mjs` через `child_process.spawn` с массивом аргументов и `shell: false`:

- новый run — `start`;
- возобновление — `resume`;
- пауза — `pause`;
- остановка — `stop`;
- итоговый пакет — `export`.

Run ID проходит существующую строгую валидацию. Пользовательские строки не объединяются в shell-команду. Одновременно может работать только один владелец конкретного run; существующие lock, PID и process fingerprint остаются источником истины.

Коллектор может продолжать работу при перезагрузке страницы панели. Если завершится сам GUI-процесс, checkpoint остаётся на G:, а следующий запуск панели определит живого владельца или предложит `Продолжить` для остановившегося run.

### 3. Read-only status API

Панель не получает состояние от stdout как от единственного источника. API читает проверенные `config.json`, `state.json`, `control.json`, `events.ndjson`, `sources`, `products`, `memberships.ndjson` и каталог `images` через безопасный слой run store.

Предусмотрены endpoints:

- `GET /api/bootstrap` — data root, наличие Chrome и список run;
- `GET /api/runs` — краткая история запусков;
- `GET /api/runs/:id` — полный snapshot выбранного run;
- `GET /api/runs/:id/events` — последние события с ограниченным размером;
- `GET /api/runs/:id/products` — постраничный список собранных товаров;
- `GET /api/runs/:id/images/:externalId` — защищённая выдача проверенного локального WebP;
- `POST /api/runs` — новый полный run;
- `POST /api/runs/:id/pause`;
- `POST /api/runs/:id/resume`;
- `POST /api/runs/:id/stop`;
- `POST /api/runs/:id/export`;
- `POST /api/runs/:id/open-folder` — запускает `explorer.exe` с проверенным абсолютным каталогом конкретного run и `shell: false`.

API не содержит endpoint для произвольного пути или произвольной команды.

### 4. Обновление интерфейса

Панель опрашивает локальный status API раз в 2 секунды, пока run активен, и реже — когда он остановлен. Этот опрос читает только локальные файлы и не создаёт запросов к донору.

Отсчёт до следующего запроса берётся из durable policy/event state. Интерфейс не запускает запрос сам и не может обходить hourly budget.

## Внешний вид

Панель использует чистый светлый интерфейс в стилистике Stylish House: белый фон, синий акцент сайта, строгая типографика, компактные статусы и хорошо различимые опасные действия. Интерфейс не копирует старый тяжёлый Bootstrap-шаблон админки.

Основной экран:

1. Верхняя строка: название, путь хранения, состояние локального сервера и кнопка открытия папки.
2. Блок выбранного run: статус, крупный общий прогресс, текущее действие и четыре управляющие кнопки.
3. Строка метрик: категории, страницы, уникальные товары, фотографии, запросы за час.
4. Таблица 46 категорий с прогрессом, текущей страницей и количеством найденных товаров.
5. Две нижние вкладки:
   - `Товары` — фото, ID, название, цена донора, категории и стадия сохранения;
   - `Журнал` — время, действие, URL и русское описание ошибки.
6. Слева или в компактном верхнем selector — история run с возможностью выбрать и продолжить незавершённый.

На узком экране метрики переходят в две колонки, таблица категорий получает горизонтальную прокрутку, а управляющие кнопки остаются крупными и доступными. Основной целевой экран — Windows desktop.

## Состояния и ошибки

Технические статусы преобразуются в понятный русский текст:

- `running` → `Сбор выполняется`;
- `paused/operator` → `Поставлено на паузу пользователем`;
- `challenge` → `Сайт показал защитную проверку`;
- `http_403` → `Сайт временно запретил доступ (403)`;
- `http_429` → `Слишком много запросов для сайта (429)`;
- `network` → `Нет соединения с сайтом`;
- `timeout` → `Сайт не ответил вовремя`;
- `hourly-budget` → `Достигнут безопасный лимит запросов за час`;
- `completed` → `Все категории и товары собраны`;
- `stopped` → `Запуск остановлен навсегда`.

После простой защитной страницы существующая логика может один раз нажать `Попробовать снова` после 10–20 секунд. GUI показывает эту стадию и не добавляет новых попыток. Полная CAPTCHA, повторный challenge, image challenge, `403` и `429` приводят к паузе.

## Безопасность

- HTTP-сервер привязан только к `127.0.0.1`.
- При старте создаётся случайный session token; mutating API требует token и проверенный same-origin запрос.
- Все изменения выполняются POST-запросами; GET остаётся read-only.
- Run ID, external ID и пути повторно валидируются существующими функциями.
- Ответы API не раскрывают содержимое браузерного профиля, cookies и секреты.
- UI не принимает произвольные URL донора: список 46 источников остаётся versioned-конфигом.
- UI не имеет функций удаления run, фотографий или checkpoints.
- Никаких scheduler, cron, Windows service или автоматического запуска при старте Windows не добавляется.
- Никакого подключения к production-БД во время сбора нет.

## Итоговый пакет и последующий импорт

После завершения кнопка `Сформировать пакет` запускает существующую полную проверку и создаёт `export.json` в каталоге run. На экране показываются путь, количество категорий, уникальных товаров, связей и фотографий, а также SHA-256 результата.

Пакет состоит из `export.json` и проверенных локальных WebP в том же run. Он совместим с существующим Laravel ingest. Загрузка на сайт и staging-review остаются отдельным контролируемым этапом. Перед первой production-мутацией обязательно создаётся и проверяется свежий бэкап БД.

## Тестирование и критерии готовности

До реализации пишутся failing tests для:

- запуска GUI только на loopback;
- создания полного run без `max-products=1`;
- безопасного spawn без shell;
- списка и выбора существующих run после перезапуска GUI;
- продолжения существующего checkpoint;
- блокировки второго владельца run;
- pause/resume/stop/export API;
- запрета произвольных путей, URL и команд;
- проверки session token и same-origin для POST;
- корректного русского отображения всех терминальных причин;
- локального polling без donor-трафика;
- постраничного просмотра товаров и защищённой выдачи WebP;
- создания export только для завершённого run.

После автоматических тестов выполняется визуальная проверка в браузере:

- desktop 1440×900;
- узкий экран 390×844;
- новый run;
- активный сбор;
- операторская пауза;
- защитная остановка;
- повторное открытие панели и продолжение сохранённого run;
- завершённый run и формирование пакета.

Готовность означает, что весь основной сценарий выполняется кнопками без терминала, интерфейс показывает реальное durable-состояние, а после принудительного завершения процесса выбранный run продолжается с последнего checkpoint без повторного скачивания уже сохранённых товаров и фотографий.

## Не входит в этот этап

- импорт пакета в production-БД из локальной панели;
- публикация товаров без staging и ручного подтверждения;
- подключение импортированных товаров к Excel-кэшу или калькулятору;
- удалённое управление через VPS или интернет;
- автоматическое решение полной CAPTCHA;
- автоматический запуск при загрузке Windows.
