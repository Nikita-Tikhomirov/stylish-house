# Импорт римских штор с управляемым staging-процессом

Дата: 2026-08-25

## Цель

Создать 46 SEO-посадочных страниц римских штор на `stylish-house.net`, собрать все уникальные товары из соответствующих разделов `rimskie.com`, сохранить первое товарное фото локально, подготовить уникальные названия и описания и обеспечить фильтрацию по характеристикам.

До ручного утверждения ни посадочные, ни товары не публикуются. Цена донора хранится только во внутреннем staging-контуре. Калькулятор и расчёты из Excel-кэша к импортированным товарам на этом этапе не подключаются.

## Подтверждённые исходные данные

- На доноре одна проверенная посадочная содержит 35 карточек на странице и 167 страниц пагинации.
- Sitemap донора содержит до 9 145 URL, похожих на римские шторы. Точный union 46 посадочных определяется только во время контролируемого обхода.
- Товары пересекаются между посадочными. Один товар должен храниться один раз и связываться с несколькими SEO-подборками.
- Карточка донора содержит стабильный numeric ID, URL, исходную цену и URL первого WebP-фото.
- Страница товара содержит описание и нормализуемые признаки: цвет, затемнение, фактуру, материал, состав, производителя, плотность, установку, тип, помещения, кант и другие значения.
- Production использует категорию `/story/` и базовую подкатегорию `/story/rimskieshtory/`. Все 46 новых slug свободны.
- Текущая модель `Product` принадлежит только одной основной подкатегории, поэтому пересекающиеся SEO-подборки требуют отдельной many-to-many связи.

## Принятые решения

### 1. Два независимых контура

Система разделяется на:

1. Локальный браузерный сборщик. Он получает страницы донора медленно, сохраняет checkpoint после каждого результата и формирует переносимый пакет данных.
2. Laravel staging и публикация. Он принимает пакет, показывает данные в админке, выполняет рерайт, проверку, утверждение и только затем создаёт production-записи.

Сборщик не подключается напрямую к production-БД. Ошибка или блокировка донора не может повредить каталог Stylish House.

### 2. Контроль нагрузки на донора

Сборщик работает последовательно, с concurrency `1`.

- HTML-запросы: случайная пауза 20–40 секунд.
- Отдельное скачивание первого фото: случайная пауза 10–20 секунд.
- Глобальный лимит: не более 120 donor-origin запросов в час по умолчанию.
- CSS, шрифты, видео, аналитика и лишние изображения блокируются после прохождения BotHunt.
- При `403`, `429`, повторном BotHunt или сетевой ошибке выполняется backoff 2, 5 и 15 минут. После третьей ошибки run автоматически ставится на паузу.
- Повторно успешно сохранённые страницы, карточки и изображения не запрашиваются.
- Любая пауза и остановка безопасны: продолжение начинается с последнего checkpoint.

Лимиты задаются конфигурацией run и могут быть увеличены только явно.

### 3. Локальное состояние сборщика

Каждый run хранится в `storage/app/imports/rimskie/<run-id>/`:

- `config.json` — лимиты и список 46 источников;
- `state.json` — статус, текущий источник, страница, очередь товаров и счётчики;
- `sources/<slug>.json` — прогресс каждой посадочной;
- `products/<external-id>.json` — разобранная карточка товара;
- `images/<external-id>.webp` — первое фото;
- `memberships.ndjson` — пары source/product;
- `events.ndjson` — журнал запросов, пауз, ошибок и изменений статуса;
- `export.json` — итоговый манифест для Laravel.

Запись checkpoint выполняется через временный файл и атомарное переименование.

CLI-команды сборщика:

- `start` — новый run или продолжение существующего;
- `status` — счётчики и последняя ошибка без обращения к донору;
- `pause` — безопасная пауза после текущего запроса;
- `resume` — продолжение;
- `stop` — корректная остановка;
- `export` — проверка целостности и формирование пакета;
- `dry-run` — не более заданного числа запросов без публикации.

### 4. Staging-модель Laravel

Добавляются таблицы:

- `catalog_import_runs` — статус run, конфигурация, счётчики, даты, ошибки;
- `catalog_import_sources` — 46 посадочных и их прогресс;
- `catalog_import_items` — donor ID/URL, исходные данные, внутреннюю цену, первое фото, переписанный контент, статус проверки и ошибки;
- `catalog_import_item_source` — пересечения товара с посадочными;
- `catalog_attributes` — определения фильтров;
- `catalog_attribute_values` — допустимые значения;
- `catalog_import_item_attribute_value` — признаки staging-товара.

Уникальные ключи:

- `(provider, external_id)` для staging-товара;
- `(import_item_id, import_source_id)` для membership;
- `(attribute_id, normalized_value)` для значения фильтра.

Повторный ingest одного пакета идемпотентен и обновляет существующий staging-run.

### 5. Рерайт

Исходный текст хранится только в закрытом staging-контуре. Публично он не используется.

Первый проход выполняет детерминированный `TemplateProductRewriter`:

- удаляет бренд и магазин донора;
- перестраивает название из типа, материала, цвета, монтажа и конструкции;
- создаёт короткое описание и расширенный текст из фактических характеристик;
- использует несколько проверенных шаблонов, выбранных стабильным hash товара;
- не выдумывает свойства, которых нет в source data;
- проверяет длину, пустые поля и совпадения с исходником;
- помечает подозрительные или слишком похожие тексты как `needs_review`.

Интерфейс `ProductContentRewriter` остаётся заменяемым. Подключение внешнего AI API не входит в текущий этап и не требуется для первого прохода.

### 6. Production-модель каталога

После ручной публикации:

- товар создаётся один раз в основной подкатегории `rimskieshtory`;
- 46 SEO-посадочных создаются как `Subcategory` внутри `/story/`;
- `catalog_collection_product` связывает товар с любым количеством посадочных;
- `catalog_product_attribute_value` хранит нормализованные признаки для фильтрации;
- `products` получает `source_provider`, `source_external_id`, `source_url`, `source_price`, `calculator_enabled` и `import_run_id`;
- `subcategories` получает `is_import_collection`.

Для существующих товаров `calculator_enabled=true`. Для импортированных — `false`.

Карточка импортированного товара не показывает цену донора и калькулятор. Вместо них выводится нейтральный CTA на запрос расчёта. Канонический URL товара остаётся один: `/story/rimskieshtory/<product-slug>/`.

### 7. Фильтрация

На странице SEO-посадочной исходный набор определяется `catalog_collection_product`. Пользовательские фильтры дополнительно ограничивают этот набор через `catalog_product_attribute_value`.

Поддерживаются:

- multi-select значения;
- логика OR внутри одного фильтра и AND между разными фильтрами;
- числовые диапазоны там, где донор отдаёт числовые значения;
- пагинация с сохранением параметров;
- счётчики значений в пределах текущей посадочной;
- серверная валидация разрешённых кодов и значений;
- отсутствие дублей товара в выдаче.

URL с параметрами фильтров получают `noindex, follow`; чистые SEO-посадочные и обычная пагинация остаются индексируемыми по действующей политике проекта.

### 8. Админка и ручной контроль

Раздел `/admin/catalog-imports` доступен только администратору.

Он показывает:

- список run и их статусы;
- количество источников, страниц, уникальных товаров, фото, дублей и ошибок;
- прогресс каждой из 46 посадочных;
- таблицу товаров с фильтрами по статусу;
- source URL и внутреннюю цену;
- первое фото;
- исходный и переписанный текст рядом;
- распознанные характеристики и memberships;
- причины `needs_review`;
- действия approve/reject/edit и пакетное утверждение;
- предварительный отчёт публикации;
- отдельную кнопку публикации только утверждённых записей;
- журнал публикации и возможность отката run.

Ни ingest, ни рерайт не меняют публичный каталог.

### 9. Публикация и откат

Публикация выполняется транзакционно и идемпотентно:

1. Проверяется свежий бэкап БД и целостность run.
2. Upsert 46 SEO-подкатегорий.
3. Upsert утверждённых товаров.
4. Копирование первого фото в public storage и генерация thumbnail.
5. Upsert membership и атрибутов.
6. Проверка URL/slug и количества связей.
7. Генерация sitemap.
8. Смена статуса run на `published`.

Откат удаляет только связи и записи, созданные конкретным run. Уже существующие товары не удаляются; их предыдущие значения восстанавливаются из audit snapshot.

### 10. 46 источников

Список хранится в versioned-конфиге с полями `label`, `source_url`, `target_slug`, `enabled`, `sort_order`. Используются ровно URL и подписи, переданные пользователем. Любое изменение списка видно в Git diff.

### 11. Тестирование

До production-кода пишутся failing tests для:

- разбора минимальных синтетических HTML fixtures категории и товара;
- извлечения donor ID, URL, цены, первого фото, описания и атрибутов;
- атомарного checkpoint и resume без повторных запросов;
- rate limit, backoff, pause/stop и лимита запросов;
- дедупликации товаров и memberships;
- идемпотентного ingest;
- уникального рерайта без бренда донора;
- публикации только approved items;
- транзакционного rollback;
- many-to-many выборки и фильтров;
- noindex параметров фильтра и sitemap чистых посадочных;
- защиты admin routes.

После автоматических тестов выполняются dry-run на одной странице и одном товаре, визуальная проверка desktop/mobile, затем длительный сбор с регулярными контрольными отчётами.

## Не входит в текущий этап

- Подключение импортированных товаров к Excel-кэшу и калькулятору.
- Использование donor price на публичном сайте.
- Копирование дополнительных фотографий галереи.
- Автоматическая публикация без ручного approve.
- Параллельный или агрессивный обход донора.
