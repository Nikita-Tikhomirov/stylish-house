## 2. Назначение задачи

Доработать существующий локальный Playwright-сборщик так, чтобы при появлении полной проверки BotHunt/SmartCaptcha он:

1. надёжно распознавал проверку;
2. сохранял точное место остановки;
3. не закрывал рабочее окно Chrome;
4. не создавал повторные запросы к донору, пока проверка не пройдена;
5. после ручного действия оператора продолжал сбор в том же процессе и с того же места;
6. после аварийного завершения процесса восстанавливался из сохранённого checkpoint и постоянного профиля Chrome.

Автоматическое решение, обход или скрытое нажатие полной CAPTCHA в эту задачу не входит. Допустимое действие программы — показать оператору точную страницу, дождаться ручного прохождения и проверить результат без новой навигации. Уже существующая обработка обычной кнопки `Попробовать снова` не должна смешиваться с полной проверкой `Я не робот`.

## 3. Что уже реализовано

- Сбор выполняется последовательно, одним процессом и одним окном Chrome.
- Профиль Chrome хранится в каталоге запуска на `G:`.
- Между HTML-запросами выдерживается 2–4 минуты, между карточкой и фотографией — 1–2 минуты.
- Действует сохранённый лимит 20 учитываемых операций за скользящий час.
- Ошибки `403`, `429`, `network` и `timeout` используют сохранённые паузы 2, 5 и 15 минут.
- `playwright-transport.mjs` отличает полную проверку от простой кнопки повторной загрузки и возвращает `DonorRequestError` с `kind === 'challenge'` и `manual === true`.
- `collector.mjs` сохраняет `status: 'paused'` и `pauseReason: 'challenge'`.
- GUI умеет отправить действующему процессу сигнал продолжения через `control.json`.
- Состояние очереди, счётчик запросов, товары и фотографии переживают перезапуск процесса.

## 4. Текущий дефект

Сейчас `runCollector()` в `scripts/rimskie-import/cli.mjs` вызывает `collector.run()` только один раз. Когда `collector.run()` возвращает `paused(challenge)`, управление сразу попадает в `finally`:

```js
await transport?.close();
await control.release(process.pid);
```

Из-за этого:

- Chrome с открытой проверкой закрывается;
- владелец запуска освобождается;
- оператору нечего подтверждать в исходном окне;
- `Продолжить` запускает новый процесс;
- новый процесс вынужден снова обращаться к URL донора;
- повтор расходует лимит запросов и может снова получить `403` или BotHunt.

Дополнительная проблема: обычный путь `Collector.#request()` вызывает `policy.beforeRequest()` до обращения к транспорту. Поэтому простое повторное выполнение `collector.run()` после ручной проверки ошибочно создаст новую резервацию, задержку и счётчик запроса, даже если нужная страница уже открыта в Chrome.

## 5. Требуемый конечный сценарий

### 5.1 Обнаружение проверки

1. `PlaywrightTransport.getHtml()` получает или видит страницу проверки.
2. Проверка классифицируется как ручная только при наличии подтверждающих признаков в видимом DOM или элементов полной CAPTCHA.
3. Транспорт сохраняет в памяти контекст незавершённой операции: исходный URL, тип страницы (`category` или `product`), видимый URL и признак `manual`.
4. До выхода из `Collector.#request()` на диск атомарно записывается контекст проверки.
5. Состояние запуска становится:

```json
{
  "status": "paused",
  "pauseReason": "challenge"
}
```

6. В `events.ndjson` появляются события `challenge` и `pause` с URL и типом страницы.

### 5.2 Ожидание оператора

1. `runCollector()` не закрывает `PlaywrightTransport` и не освобождает владельца запуска.
2. Окно Chrome остаётся открытым на странице проверки.
3. GUI показывает состояние `Требуется проверка`, точный URL и инструкцию пройти проверку в открытом Chrome.
4. Процесс ждёт изменения `control.json`, не обращаясь к `rimskie.com`.
5. Ожидание реализовать локальным циклом с интервалом около одной секунды. Этот цикл не считается donor-запросом.
6. Команда `Пауза` оставляет процесс в ожидании.
7. Команда `Остановить` должна завершить запуск, закрыть транспорт и освободить владельца.
8. Команда `Продолжить` для живого владельца только снимает флаг `pause`; второй сборщик не запускается.

### 5.3 Проверка результата ручного действия

После нажатия `Продолжить` живой процесс сначала проверяет уже открытую страницу, не вызывая:

- `page.goto()`;
- `page.reload()`;
- `policy.beforeRequest()`;
- резервирование новой операции;
- увеличение `requestCount`;
- обычную задержку 2–4 минуты.

Требуемый результат проверки:

- если полная CAPTCHA всё ещё видна — снова вернуть `paused(challenge)`, оставить Chrome открытым и продолжить ждать;
- если открыт ровно ожидаемый URL и DOM соответствует ожидаемой странице категории или товара — использовать текущий HTML как результат исходной незавершённой операции;
- если URL изменился, origin не `https://rimskie.com`, тип страницы не совпадает или DOM невалиден — перейти в диагностическую паузу/ошибку без новой навигации;
- после успешной проверки очистить контекст незавершённой проверки и продолжить обычную очередь.

Успешное чтение уже открытого DOM не является новым сетевым запросом. Новую резервацию создавать нельзя, но `policy.recordSuccess()` нужно вызвать ровно один раз в момент успешного завершения исходной операции: первоначальная навигация была зарезервирована, однако из-за проверки ещё не была отмечена успешной.

### 5.4 Аварийный перезапуск

Если процесс или компьютер завершились во время проверки:

1. checkpoint остаётся `paused(challenge)`;
2. профиль Chrome остаётся в `<run-dir>\profile`;
3. повторный запуск через GUI открывает тот же профиль;
4. поскольку старой живой страницы в памяти уже нет, допускается только обычное безопасное восстановление через сохранённый URL после действующего backoff и лимита;
5. счётчик 20 операций в час и уже сохранённые timestamps не сбрасываются;
6. параллельный второй процесс для того же `run-id` запрещён.

## 6. Требуемые изменения по файлам

### `scripts/rimskie-import/lib/playwright-transport.mjs`

Добавить отдельный публичный метод, например:

```js
resumePendingManualChallenge(url, { kind })
```

Контракт метода:

- возвращает `{ handled: false }`, если в текущем транспорте нет подходящей ручной проверки;
- проверяет точное совпадение исходного URL и `pageKind`;
- читает `page.url()` и `page.content()` без навигации;
- при всё ещё видимой проверке выбрасывает типизированный `DonorRequestError` с `kind: 'challenge'` и `manual: true`;
- при нормальной ожидаемой странице возвращает `{ handled: true, html }`;
- при чужом URL или origin выбрасывает `invalid_url`;
- после успеха очищает `pendingChallenge`, `activeOperation` и переводит маршрутизацию из режима `challenge` в `idle`;
- не нажимает `Я не робот`, не вызывает `goto`, `reload` или автоматический CAPTCHA-solver.

Расширить `pendingChallenge` минимум до:

```js
{
  url,
  visibleUrl,
  pageKind,
  manual,
  detectedAt
}
```

Не ослаблять текущую URL-политику и блокировку незапланированных запросов.

### `scripts/rimskie-import/lib/collector.mjs`

До `policy.beforeRequest(kind)` добавить узкую ветку восстановления только для HTML:

1. вызвать `transport.resumePendingManualChallenge(url, { kind: pageKind })`, если метод существует;
2. если `handled === false`, идти по существующему пути запроса;
3. если получен HTML, передать его существующему парсеру без новой резервации;
4. если проверка всё ещё активна, снова сохранить `paused(challenge)`;
5. не увеличивать `requestCount`, а `recordSuccess()` вызвать ровно один раз только после получения нормального HTML исходной операции.

Для этого не передавать анонимную функцию без метаданных. Добавить в `#request()` явный `pageKind` или объект операции, чтобы транспорт мог проверить `category`/`product`.

Сохранять в `state.json` безопасный диагностический объект без cookies и токенов, например:

```json
{
  "pendingChallenge": {
    "url": "https://rimskie.com/catalog/...",
    "pageKind": "category",
    "sourceSlug": "rimskie-shtory-na-arochnoe-okno",
    "externalId": null,
    "detectedAt": "2026-08-28T00:00:00.000Z"
  }
}
```

Очищать `state.pendingChallenge` после успешного продолжения, окончательной остановки или диагностической ошибки.

### `scripts/rimskie-import/cli.mjs`

Переделать `runCollector()` в цикл жизненного цикла одного транспорта:

```text
claim owner
open transport once
run collector
if result != paused(challenge): finish
persist pause flag
wait for Continue or Stop
if Continue: run collector again with acknowledgeChallenge=true
if Stop: let collector checkpoint stopped
close transport once
release owner once
```

Обязательные свойства:

- `transport.close()` вызывается ровно один раз при фактическом завершении процесса;
- `control.release()` вызывается ровно один раз после закрытия транспорта;
- во время ожидания `ownerPid` остаётся живым;
- повторная команда GUI `resume` получает `resume-signaled`, снимает паузу и не создаёт второй браузер;
- цикл ожидания должен принимать внедряемые `sleep`/`pollInterval` для быстрых unit-тестов;
- исключение в ожидании всё равно закрывает транспорт и освобождает владельца через `finally`.

### `scripts/rimskie-import/gui/status-service.mjs`

Добавить в snapshot безопасные поля:

```json
{
  "challenge": {
    "url": "https://rimskie.com/...",
    "pageKind": "category",
    "sourceLabel": "На арочное окно",
    "externalId": null
  }
}
```

Не передавать в API cookies, заголовки авторизации, содержимое профиля или storage браузера.

### `scripts/rimskie-import/gui/public/app.js`

Для `pauseReason === 'challenge'` показывать отдельный баннер:

```text
Сайт просит ручную проверку.
Пройдите её в открытом окне Chrome, затем нажмите «Продолжить».
Повторных запросов до этого не будет.
```

Кнопка `Продолжить` должна быть активна. После её нажатия GUI показывает `Проверяем открытую страницу…`, а затем новое состояние сервера.

## 7. Автоматические тесты

Сначала добавить тесты, убедиться, что они падают на текущем коде, и только потом менять реализацию.

### Транспорт

Файл: `tests/js/rimskie-import-donor-boundary.test.mjs`

Обязательные случаи:

1. `resumePendingManualChallenge()` читает текущий DOM и не вызывает `goto`, `reload` или `click`.

3. После ручного прохождения возвращается текущий HTML ожидаемой категории.
4. Чужой origin, другой URL и неправильный `pageKind` отклоняются.
5. После успеха режим маршрутизации возвращается в `idle`.

## 9. Ручная приёмка

Проводить только после зелёных тестов и не создавать серию запросов к донору.

1. Запустить `start-rimskie-gui.cmd`.
2. Выбрать существующий тестовый запуск.
3. Дождаться естественной проверки BotHunt или использовать полностью локальный fake/test fixture.
4. Убедиться, что GUI показывает `Требуется проверка`, а Chrome остаётся открытым.
5. Нажать `Продолжить`, не проходя проверку.
6. Убедиться, что состояние осталось `paused(challenge)`, `requestCount` не изменился и `page.goto()` не был вызван.
7. Пройти проверку вручную в открытом Chrome.
8. Нажать `Продолжить`.
9. Убедиться, что текущий DOM принят без нового запроса, затем сбор продолжается с сохранённого товара или категории.
10. Перезапустить GUI и проверить, что checkpoint и лимит запросов сохранились.

## 10. Запреты

- Не подключать CAPTCHA-solving сервисы, прокси-ротацию, подмену fingerprint или скрытый браузер.
- Не нажимать автоматически `Я не робот`.
- Не ослаблять проверку origin/URL и сетевую границу Playwright.
- Не сбрасывать backoff, timestamps или `requestCount` при продолжении.
- Не создавать scheduler, cron, Windows service или фоновую автозадачу.
- Не писать рабочие данные на диск `C:`.
- Не читать и не экспортировать cookies, local storage, пароли или другие данные браузерного профиля.
- Не изменять production-базу в рамках этой задачи.
- Не удалять и не перезаписывать несвязанные изменения пользователя, включая `.phpunit-worktree-bootstrap.php`.

## 11. Definition of Done

Задача завершена только когда:

- полная проверка переводит запуск в `paused(challenge)`;
- Chrome и процесс-владелец остаются живыми;
- без ручного прохождения нет нового donor-запроса;
- ручное прохождение принимается из текущего DOM без новой навигации;
- очередь, товар, категория и лимит запросов сохраняются;
- остановка и аварийный перезапуск безопасны;
- GUI однозначно объясняет оператору действие;
- все перечисленные тесты и глобальный `smoke` проходят;
- изменения закоммичены осмысленным `fix:`-коммитом и отправлены в `origin/codex/rimskie-import`;
- README и операторская инструкция обновлены, если поведение кнопок изменилось.

Перед любыми будущими изменениями базы сайта обязательно создать и проверить свежий бэкап базы. В рамках этого ТЗ база не изменяется, поэтому резервное копирование базы не требуется.
